# 脚本开发规范

本规范适用于管理入口、功能脚本和 Shell 公共库。当前已实现管理入口、共享命令辅助层和首批网络功能脚本。

## 1. 运行环境

- 目标系统为使用 GNU 用户空间的 Linux VPS。
- 默认解释器为 Bash，最低支持版本为 Bash 4.4。
- 依赖非基础命令前必须先检查，并在缺失时给出明确安装提示；支持自动安装时必须要求显式授权。
- 发行版特有行为必须先检测系统能力或发行版，不得仅凭猜测执行。
- 不假定调用者的当前工作目录；所有项目内路径均从脚本自身位置解析。

每个可执行脚本应启用 `set -Eeuo pipefail`，并显式设置安全的 `IFS`。预期可能失败的探测必须放入条件判断或显式处理退出状态，不得依赖关闭严格模式。

## 2. 命名与布局

- 文件和目录统一使用小写英文。
- 多词名称使用 kebab-case。
- 功能脚本路径为 `commands/<domain>/<action>.sh`。
- 动作名称优先采用动词或“动词-对象”，如 `inspect`、`update-packages`。
- 公共函数使用带模块前缀的 snake_case，避免覆盖 shell 内建命令和常见环境变量。
- 常量使用只读的大写 snake_case；局部变量使用小写 snake_case。

不得创建含糊的 `utils.sh` 或 `common2.sh`。公共库应按职责命名，例如未来可采用 `logging.sh`、`platform.sh`。

## 3. 命令接口

每个功能脚本必须：

- 支持 `--help`，只展示帮助且返回成功。
- 拒绝未知参数和缺少值的选项。
- 使用 `--` 终止选项解析，并安全处理含空格的参数。
- 明确标注必填参数、默认值、影响范围、权限要求和是否支持演练。
- 不在交互提示中暗设默认同意；非交互环境下不得等待输入。
- 不依赖入口私有变量，独立执行时也能完成环境检查并给出可诊断错误。

统一入口规划支持以下全局语义，功能脚本实现时应保持一致：

| 选项或上下文 | 语义 |
| --- | --- |
| `--dry-run` | 展示将执行的变更，不修改系统 |
| `--install-deps` | 明确允许按当前动作安装缺失的软件包依赖；不绕过平台能力门禁 |
| `--yes` | 仅跳过允许自动确认的提示，不绕过安全校验 |
| `--non-interactive` | 禁止读取终端；缺少必要输入立即失败 |
| `--quiet` | 压制非必要的人类可读信息，不压制错误 |
| `--verbose` | 增加诊断信息，不泄露秘密 |

某个命令不支持其中一项语义时，必须明确拒绝，而不是静默忽略。

## 4. 输出与日志

- `stdout` 只用于正常结果和用户请求的机器可读数据。
- `stderr` 用于进度、警告、诊断和错误。
- 日志必须包含级别和简洁上下文，不依赖颜色表达唯一信息。
- 仅在连接终端且用户未禁用颜色时输出 ANSI 颜色。
- 不输出密码、令牌、私钥、完整认证头或未经脱敏的配置。
- 机器可读输出必须由显式参数启用，并在命令登记文档中定义字段和版本。

错误信息应说明“什么失败、影响什么、用户下一步可以做什么”，同时保留底层命令的有效诊断。

## 5. 退出码

所有脚本使用以下基础退出码；命令特有退出码需登记，不得与基础含义冲突。

| 退出码 | 含义 |
| ---: | --- |
| `0` | 成功；目标状态已经满足也属于成功 |
| `2` | 参数或用法错误 |
| `3` | 前置条件不满足或依赖缺失 |
| `4` | 当前权限不足 |
| `10` | 配置无效 |
| `20` | 外部命令或远端服务失败 |
| `30` | 操作部分完成，需要人工检查或恢复 |
| `70` | 未分类的内部错误 |
| `130` | 用户中断 |

管理入口应原样返回功能脚本的退出码。不得用 `exit 0` 掩盖已发生的失败。

## 6. 安全要求

- 默认采用最小权限；只有需要特权的具体步骤才请求 root 权限。
- 禁止使用 `eval` 执行用户输入，禁止把未验证输入拼入 shell 命令。
- 参数必须通过数组传递，路径和变量展开必须加引号。
- 危险操作必须验证规范化后的目标，拒绝空路径、根目录、家目录和范围过宽的通配符。
- 删除、覆盖、重启、封禁访问或更改防火墙前必须提供影响说明，并支持适当的确认或演练机制。
- 写配置采用“临时文件、校验、权限设置、原子替换”的流程；替换前保留可识别的备份或提供恢复步骤。
- 下载内容应使用 HTTPS，并在有官方校验信息时验证校验和或签名。
- 临时文件使用安全方式创建，并确保退出时清理。
- 并发执行可能破坏状态时必须使用锁，超时后给出可诊断错误。

任何可能中断 SSH 连接的操作，都必须先验证新配置、保留现有会话的恢复路径，并在帮助中显著说明风险。

## 7. 幂等、事务与恢复

- 同一命令重复执行应收敛到同一目标状态。
- 执行变更前先检测当前状态，避免无意义重启或重复追加配置。
- 将“检查、计划、应用、验证”划分为可识别阶段。
- 多步变更必须说明失败后的系统状态；可安全回滚时自动回滚，否则返回 `30` 并输出人工恢复步骤。
- 不可逆操作必须在帮助和确认信息中明确标注。

## 8. 依赖与可移植性

- 优先使用系统通常已有的工具，新增依赖必须在命令登记中说明理由。
- 外部命令必须在执行前完成能力检查；版本差异影响行为时检查版本。
- 依赖安装统一使用共享接口，只允许固定的软件包管理器、固定参数数组和经过校验的软件包名称；当前适配 `apt-get`、`dnf5`、`dnf`、`yum`、`apk`、`pacman` 与 `zypper`。
- 功能必须先完成参数校验和不可安装的平台门禁，再安装当前动作真正缺少的工具；不得把 Linux、init 系统、CPU 架构、内核能力、XDP/BPF 或目标功能本体伪装成普通包依赖。
- 未提供 `--install-deps` 时只报告缺失工具并返回 `3`；实际安装要求 root。与 `--dry-run` 同时使用时只展示包管理器计划，不执行安装；若缺失工具会妨碍后续安全验证，命令应停止并提示安装后重跑。
- 发行版差异应封装在平台适配函数中，功能脚本不应散布大量系统名称判断。
- 不解析面向人类且不稳定的命令输出；优先使用稳定参数或机器可读格式。

## 9. 质量门槛

未来每个脚本合并前至少满足：

以下检查和测试只能通过 `ssh host-vps-scripts` 在专用真实环境中执行，禁止在当前系统或 WSL 中运行：

- `bash -n` 语法检查通过。
- ShellCheck 无未说明的错误；必要的抑制必须就地写明原因。
- 格式化工具检查通过，统一采用项目确定的 shfmt 配置。
- 参数错误、缺少依赖、权限不足、重复执行和中断路径均有测试。
- 有系统变更的功能在 `host-vps-scripts` 中完成真实环境集成验证。
- 帮助文本、命令登记和行为一致。
